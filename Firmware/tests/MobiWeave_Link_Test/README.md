# 空口联调操作手册（第一版）

目标：在不依赖正式协议实现（ACK、重传、去重还没写）的前提下，用两颗板子把**链路**和**报文**先验证掉。

适用范围：ESP32-S3 N16R8 + DX-LR22-433T22D ×2，Arduino IDE。
预计耗时：第一次做 2～3 小时，其中一半时间通常花在模块配置和供电上。

> 本手册里的 `.ino` 只用 PC 上的 g++ 做过语法和格式串检查（A/B 两个 ROLE 变体都通过），
> **没有用 Arduino-ESP32 工具链真正编译过，也没有实机验证**。第一次烧录请严格按 STAGE 1 走。

## 1. 接线

### 1.1 主接线（A 板、B 板一样）

| 模块引脚 | 接到 ESP32-S3 | 说明 |
|---|---|---|
| VCC | 3V3（或外部 3.3V） | 模块附近并 100µF 电解 + 0.1µF 瓷片 |
| GND | GND | 必须共地 |
| TXD | **GPIO18** | 模块发 → 板收 |
| RXD | **GPIO17** | 板发 → 模块收 |
| M0 | GPIO4 | 代码拉低 |
| M1 | GPIO5 | 代码拉低 |
| AUX | 不接 | — |

**TX/RX 一定交叉**：模块 TXD 接板子 RX，模块 RXD 接板子 TX。这是新手第一个坑。

### 1.2 供电

- 优先用外部 3.3V 电源给模块，ESP32 自己走 USB。**不要**从板子的 3V3 引脚给两个模块同时供电。
- 发射瞬间电流可到 100mA 以上，电源限流太小会表现为“发几帧就复位”。
- 上电顺序：先接好所有线 → 再上电 → 最后插 USB 看日志。

### 1.3 上电前用万用表确认

1. 3V3 与 GND 之间**不短路**（电阻不应接近 0Ω）。
2. 模块 VCC 上量到的是 3.3V，不是 5V。
3. GPIO17/18 没有和电源短接。

## 2. 配置两个模块（最容易失败的一步）

DX-LR22-433T22D 使用厂家 AT 指令体系，不应套用其他品牌模块的 `C0/C1/C2` 寄存器命令，也不假定存在 ADDH/ADDL 或 NETID 字段。

官方依据：[DX-LR22-433T22D 串口应用指导 V2.0](https://www.szdx-smart.com/static/upload/2025/12/11/202512113214.pdf)。若实际模块固件不同，以对应版本说明为准。

先分别记录两个模块的串口波特率、校验方式、速率等级、工作信道、传输模式、分包长度、RSSI 附加设置、密钥设置，以及模式控制方式。

手册默认串口为 9600/8/N/1、速率等级 LEVEL2、透明传输。默认值只是起点，必须读取实际配置确认。

厂家透明传输示例依次使用：

1. `+++` 进入 AT 模式。
2. `AT+MODE0` 选择透明传输。
3. `AT+LEVEL2` 选择相同速率等级。
4. `AT+CHANNEL01` 选择相同信道（这是手册示例，不是本项目强制信道）。
5. `AT+RESET` 重启使相关配置生效。

指令行尾、响应、参数查询和模式切换时序按手册执行；不要将配置指令与正在发送的业务数据混在一起。

当前草图只收发数据，没有模块配置功能。需要先通过厂家工具或独立串口配置流程完成设置。

两端透明通信需要兼容的射频、密钥及工作模式；模块地址不是应用协议的 node_id，不能把“地址必须相同”当作通用要求。当前解析器不处理模块额外附加的 RSSI 字节，首轮联调应关闭该附加输出。

M0/M1 是否生效受模块控制方式设置影响。草图将两脚拉低不能替代读取配置；AUX 首版未接，发送节奏还需通过实测核对。

**完成标准**：保存两端参数查询的原始响应及固件版本，确认实际兼容后再联调。

### 3.6 怎么确认烧对了

分别打开两个串口监视器（115200），上电后应看到：

A 板：
```
=== MobiWeave link test ===
ROLE=A(sender)  STAGE=1(raw-ping)
USB=115200 LoRa=9600 TX=17 RX=18 M0=4 M1=5
命令：1/2/3 切阶段，r 统计，t 再打印样例
```

## 4. 第 0 关：单板自检（只插 A 板，不接模块）

**目的**：先证明“板子算出来的字节 = 文档里的样例”。这一步不涉及任何无线因素。

1. 只插 A 板（`MW_ROLE 0`），**先不接模块**。
2. 串口监视器里发一个字符 `2`，会回显 `STAGE -> 2(protocol-frame)`。
3. 之后每秒出现：

```
TX  39 bytes: A5 5A 01 01 1F 00 01 00 02 00 01 00 03 00 07 00 00 00 0C 00 00 00 02 00 00 00 00 60 EA 00 00 01 03 01 53 4F 53 BA D0
```

4. 把这几十行复制保存成 `capture-stage0.txt`，在电脑上跑：

```powershell
python tools/mwframe.py --log capture-stage0.txt
```

**通过标准**：输出里有 `DATA 1->3 via 1->2 #(1,7,12) ... payload='SOS'`，且没有“丢弃”。

> 注意：启动时的 `DOC SAMPLE:` 那行也含十六进制，`--log` 会把它也算一帧，
> 所以“解析帧数”通常比实际发送次数多 1，这是正常的。

**不通过**：说明板端编码或 PC 解码器有问题，先解决。这一步不过，后面无线出问题会分不清是协议还是链路。

## 5. 第 1 关：裸透传（先不谈协议）

**目的**：只验证“A 发什么，B 就收到什么”。

1. A 板：串口里按 `1`
2. B 板：串口里按 `1`
3. 两块板各自插 USB，开两个串口监视器（两个不同的 COM 口）

（两块板都已经烧好，不用重新上传。按 `1` 后有回显 `STAGE -> 1(raw-ping)`。）

**A 侧预期**（每秒一行）：

```
TX  7 bytes: 50 49 4E 47 20 31 0A
```

**B 侧预期**（每秒两行，序号递增）：

```
RX  7 bytes: 50 49 4E 47 20 31 0A
    text="PING 1 "
```

`50 49 4E 47 20 31 0A` = `PING 1\n`，共 7 字节。两边完全一样就算这条链路通了。

**失败对照表**：

| 现象 | 先查 |
|---|---|
| B 完全没有输出 | 模块串口波特率（`LORA_BAUD`）；TX/RX 是否交叉；有没有共地 |
| B 输出乱码 | 两边波特率不一致；空中速率不一致 |
| 只收到第一行就停 | 供电掉压；加电容/换独立电源 |
| 收到但内容截断 | 模块分包、缓冲或串口丢字节；先拉大发送间隔并保存原始日志 |
| 两板距离 1 米内都收不到 | 天线没接；M0/M1 电平停在配置模式 |

## 6. 第 2 关：协议帧（对文档逐字节）

**目的**：把“文档里的样例”变成“线上真实收到的字节”。

1. A 板：串口里按 `2`
2. B 板：串口里按 `2`（两边都先回到 2，顺序无所谓，但两块板要一致）

**A 侧**每秒一条 `TX  39 bytes: A5 5A ...`

**B 侧**预期：

```
RX  39 bytes: A5 5A 01 01 1F 00 01 00 02 00 01 00 03 00 07 00 00 00 0C 00 00 00 02 00 00 00 00 60 EA 00 00 01 03 01 53 4F 53 BA D0
    DATA sender=1 receiver=2 source=1 dest=3
         boot=7 sequence=12 pri=2 age=0 life=60000 hop=1/3 type=1 payloadLen=3
    MATCH doc sample
```

**通过标准**：B 侧连续出现 `MATCH doc sample`，并且按 `r` 看到的 `frames` 在涨、`badCrc` 保持 0。

再做一次计数实验：让 A 发 100 条（约 100 秒），按 B 的 `r`，记录：

```
STAT bytes=... frames=... crcOk=... badCrc=... pending=0
```

当前 STAGE 2 重复发送相同消息编号，且切阶段不会清零接收统计。因此不能直接用累计 `crcOk / 100` 声称唯一消息交付率。

先记录测试开始/结束的两端计数，保存对应区间日志：以 A 实际 TX 行数为发送次数，以 B 对应区间新增的有效 DATA 帧数为接收次数，只报告“有效帧接收计数比”。重复接收可能使该值偏高。正式交付率实验需要每条消息使用不同 sequence、按完整消息编号去重，并排除启动样例和 ACK。

## 7. 第 3 关：长度上限（回答“168 字节到底能不能发”）

**目的**：验证不同长度应用帧能否完整传递，不将应用帧长度等同于单个空中包长度。模块可能自行分包。

1. A 板：串口里按 `3`
2. B 板：串口里按 `3`

A 会依次发载荷 0、12、24…132 字节的帧，即整帧 **36、48、…、168** 字节，每个长度间隔 1 秒，12 秒一轮。

B 侧会打印 `RX  N bytes:` 和 `payloadLen=`。填这张表（连续观察 3 轮以上）：

| 整帧长度 | A 发了 | B 收到 | 收到的长度 | CRC 是否通过 |
|---|---|---|---|---|
| 36 | | | | |
| 48 | | | | |
| … | | | | |
| 168 | | | | |

**判读**：

- 所有长度都收到且 CRC 通过 → 模块支持 168 字节，`body` 上限 160 可以保留。
- 某个长度起持续失败 → 记录失败边界，进一步排查模块分包、缓冲、发送间隔和配置，不能直接认定为单包硬上限。
- 大帧变成两段都能收到 → 模块自己在分包，接收端靠流式解析能拼回来（你已经实现了），但要注意**到达率**。
- 大帧 CRC 失败 → 分别检查串口丢字节、附加 RSSI、缓冲和供电；记录条件后逐项排查，不能只由 CRC 错误定位空口原因。

## 10. 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 串口监视器一片空白 | USB CDC On Boot 没开 | 改设置重新上传 |
| 上传失败 | 板子进了下载模式失败 | 按住 BOOT 点 RST 再上传 |
| 烧完立刻重启循环 | 原因需结合启动日志判断 | 先断开外设核对；若为 XMC startup fail，单独查 Flash 兼容性 |
| 两块板都能发但互相收不到 | 射频、工作模式或密钥等配置不兼容 | 按 DX-LR22 手册重读参数对比 |
| 收到 `DROP header` | 长度字段或版本不对 | 先用第 0 关确认板端编码 |
| 收到 `DROP crc` | 空中传输误码/波特率不稳 | 降空中速率、缩距离、查天线 |
| B 侧 `pending` 一直是 9 | 半帧后没有后续字节 | 说明模块把帧截断了，看第 3 关结果 |

## 11. 日志输出（JSONL）

草图同时输出两种行：人类可读的调试行和 [日志 V1](../../../docs/protocol/log-v1.md) 的 JSONL 行。JSONL 行以 `{` 开头，调试行不是 JSON。

当前只实现四个事件：

| 事件 | 何时产生 | 关键字段 |
|---|---|---|
| `BOOT` | 上电或收到 `RUN` 命令后新开会话 | node_id、session_id |
| `DATA_TX` | 每发出一帧 DATA | peer_id、attempt、frame_bytes、channel |
| `DATA_RX` | 每成功解析一帧 DATA | peer_id、frame_bytes、channel |
| `FRAME_REJECTED` | 帧头或 CRC 校验失败 | frame_type、原因码、channel |

`node_id` 由 `MW_ROLE` 推出：A 板为 1，B 板为 2。

### 设置 run_id

`run_id` 必须由上位机下发，板端无法自己知道属于哪次实验：

```
RUN exp-2026-11-23-a
```

回显 `RUN_OK exp-2026-11-23-a`，同时开启新会话（换 `session_id`、`event_seq` 从 1 重新开始、补一条 `BOOT`）。
未设置时 `run_id` 为 `unset`，按规范这类会话不得作为正式实验数据。

### 只要 JSONL 时

按 `v` 关闭人类可读行，串口只剩 JSONL。再按一次恢复。

串口监视器启动时那几行 banner 是非结构化行，抓包里会保留；校验时它们按「非 JSON 行」跳过。

### 校验

```powershell
python tools/mwlog_check.py capture.txt
python tools/mwlog_check.py --strict capture.txt   # 要求整份文件全是 JSONL
```
