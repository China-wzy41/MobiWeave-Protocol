# 协议与日志｜B 负责统一

本文件是设计与验收要求，**不是已冻结协议，也不是已实现功能**。B 在 [#6](https://github.com/China-wzy41/MobiWeave-Protocol/issues/6) 中交付具体字段类型、单位、范围、字节序、编码和样例；A/C/D 共同核对，正式交付 2026-11-30。

## 先统一什么

|内容|必须说清楚|
|---|---|
|版本与帧边界|如何识别一帧、最大长度、最大载荷、大小端、编码、长度检查、CRC及坏帧处理|
|消息身份|源节点、目的节点、消息类型、唯一消息编号；重启后序号不能与历史消息冲突|
|重要程度|优先级有哪些、如何排序、同级如何处理|
|有效期|消息年龄与允许存活时间、到期判据、时钟依据；重启与跨节点转发不能重置寿命|
|转发限制|hop_limit 表示最多转发次数，hop_count 表示已经转发次数；不与有效期混用|
|业务内容|载荷长度、编码、内容完整性校验与错误处理|
|后续分片|M2 再定义分片编号、总片数、重组与续传；不要求本月实现|

先短消息后分片。当前是自定义轻量协议，参考 DTN 思路不等于完整 BPv7 兼容。

## 收发步骤的共同理解

下图用于讨论流程，具体状态、超时、返回码由 B 在字段文档中冻结。

```mermaid
flowchart LR
  A[创建消息并记录编号] --> B[检查有效期和转发限制]
  B --> C[写入队列]
  C --> D[有接触机会时发送]
  D --> E[接收方校验并查重]
  E --> F[保存或拒绝并返回明确状态]
  F --> G[目的节点完整校验并首次交付]
```

三种确认必须分开：**本跳收到、已经持久保存、目的应用最终交付**。一次普通 ACK 不能自动显示为最终送达。

M1 要写清超时、有限重试、重试耗尽原因、重复与乱序行为。超时依据实际空口时间和处理开销设置。缓存要有容量/内存上限、满时拒绝或淘汰规则、持久化写入成本、断电恢复与去重规则。见 [#10](https://github.com/China-wzy41/MobiWeave-Protocol/issues/10)、[#12](https://github.com/China-wzy41/MobiWeave-Protocol/issues/12)。

## 日志必须能连接各模块

每条日志至少能够回答“哪次实验、哪个节点、哪条消息、发生了什么、何时发生、结果如何”。

|字段组|需定义的信息|
|---|---|
|来源|格式版本、run_id（实验编号）、REAL/SIM/ESTIMATED 来源标记、代码/配置/策略版本|
|对象|节点编号、消息编号；有分片时包含分片编号|
|时间|单调时间、时间单位、时钟基准、同步或偏差说明；最后更新时间|
|事件|创建、发送、接收、缓存、转发、交付、过期、丢弃、失败及原因|
|状态|队列状态、无线参数、接收观测、已知的电量和位置|

RSSI/SNR 属于接收观测，不是发送前已知的业务必填值。没有测量就写 unknown/null；模拟值必须标明模拟。没有电量/定位测量时不要补造数据。日志本身也消耗传输资源，后期应计入开销。

## 交付样例

正常帧、错误长度、坏 CRC、重复消息编号、设备重启后序号、半帧和乱序/延迟样例；再给一条消息从创建到交付的完整事件记录。

B 给出预期行为，C 用模拟核对，A 用板端核对，D 用同一组样例做显示与保存。格式变更记录版本和迁移方式；串口、模拟、无线只换输入适配，不另建冲突协议。
