# MobiWeave 通信协议 V1 草案

状态：讨论稿，尚未冻结，尚未完成代码验证。

## 1. 目标与范围

硬件：ESP32-S3 N16R8 + DX-LR22-433T22D。
开发环境：Arduino。

第一阶段实现短消息的编码、解析、校验、确认、有限重传和去重。
本阶段先定义消息与日志格式，为硬件、仿真、上位机提供共同接口。
分片与断点续传在后续阶段设计。

## 2. 协议帧需要定义的内容

以下为候选内容，最终字段布局、类型和长度待讨论。

| 内容 | 含义 | 待确定事项 |

| 协议版本 | 区分不同版本的报文 | 字段长度、未知版本处理 |
| 帧类型 | 区分数据帧与 ACK 等控制帧 | 类型编号 |
| 长度 | 判断报文是否完整和是否合法 | 计数范围、最大长度 |
| 本跳发送与接收节点 | 标识当前无线传输的双方 | 地址格式 |
| 消息源与最终目的节点 | 标识消息最初来源与最终去向 | 地址格式 |
| 消息唯一编号 | 用于追踪、去重和确认 | 重启后不重复的生成方案 |

| CRC | 检查报文完整性 | 算法、参数、覆盖范围和字节序 |

## 3. 基础收发流程

1. 发送节点创建消息并分配唯一编号。
2. 检查有效期、跳数限制和队列容量。
3. 编码并发送数据帧，启动 ACK 等待计时。
4. 接收节点完成帧解析、长度检查和 CRC 校验。
5. 校验通过后，检查消息是否重复。
6. 根据接收结果返回对应状态的 ACK。
7. 发送节点根据 ACK 更新状态。
8. 超时后有限重试，达到上限后记录失败原因。

待确定：ACK 字段、超时依据、重试上限和退避规则。

## 4. 确认状态

必须区分：
- 本跳接收成功。
- 已持久保存。
- 目的应用最终交付。

第一版普通 ACK 的准确语义待确定。
未实现持久化时，不得声称已经持久保存。
中间节点的 ACK 不代表最终目的节点收到。

## 5. 异常处理

| 情况 | 需要明确的行为 |
|---|---|
| 长度不合法 | 丢弃与重新寻找帧边界的规则 |
| CRC 错误 | 丢弃、日志和是否响应 |
| 半帧 | 等待后续字节及解析超时 |
| 重复消息 | 不重复交付，是否再次回复 ACK |
| ACK 超时 | 重试、退避和最终失败状态 |
| 队列已满 | 拒绝或淘汰规则及反馈 |
| 消息过期 | 停止发送和清理规则 |
| 节点重启 | 编号、缓存和去重状态如何恢复 |

## 6. 日志格式

日志与无线报文分别定义，不要求把全部日志字段通过无线发送。

候选日志字段：
- format_version：日志格式版本
- run_id：实验编号
- source_kind：REAL / SIM / ESTIMATED
- code_version、config_version、strategy_version：版本信息
- node_id：产生日志的节点
- message_id：关联消息
- monotonic_ms：节点本地单调时间，单位毫秒
- event：创建、发送、接收、缓存、转发、交付、丢弃或失败
- result、reason：结果与原因

不同节点的本地时间不能直接当作已经同步。
未测量的 RSSI、电量和位置使用 null 或明确的未知值。

## 第一轮具体设计：消息身份与转发地址

状态：建议方案，待团队核对和代码验证。

### 节点地址

每个节点配置不同的 node_id。
节点地址的字段长度和保留值待确定。

### 消息唯一编号

建议由以下三部分组成：
- source_id：最初创建消息的节点编号。
- boot_counter：持久化的启动计数。
- sequence：本次启动内递增的消息序号。

新建消息分配新编号。
重传和中继转发均保留原编号。

启动计数必须在创建消息前可靠更新。
擦除存储、编号耗尽和身份重新配置的处理需进一步定义。

### 本跳地址与最终地址

本跳发送者、接收者随转发过程变化。
消息源与最终目的节点保持不变。

示例：
A(1) → M(2) → B(3)

第一跳：发送者 1，接收者 2，消息源 1，最终目的 3。
第二跳：发送者 2，接收者 3，消息源 1，最终目的 3。

### 去重原则

接收方使用完整消息编号识别重复消息。
重复消息不得再次交付给业务层。
重复消息的 ACK 响应和去重记录保留时间后续定义。
## 第二轮具体设计：基础字段类型

状态：建议方案，待团队核对，尚未完成代码验证。

### 编码约定

无线报文采用二进制编码。
多字节整数统一采用小端序。
字段按协议规定的顺序逐项编码，不直接发送 C++ 结构体内存。

小端序示例：
数值 0x1234 在线路上依次发送字节 0x34、0x12。

本节只确定部分基础字段。
完整帧布局、帧边界、长度字段和 CRC 后续定义。

### 节点地址

节点地址使用 uint16_t，占 2 字节。

- 1～65534：普通节点地址。
- 0：无效地址。
- 65535：预留，本阶段不用于业务消息寻址。

同一次实验中，各节点地址必须唯一。
sender_id、receiver_id、source_id、destination_id
均使用上述地址类型。

### 消息唯一编号

| 字段 | 类型 | 字节数 | 规则 |
|---|---|---|---|
| source_id | uint16_t | 2 | 最初创建消息的节点 |
| boot_counter | uint32_t | 4 | 持久化启动计数 |
| sequence | uint32_t | 4 | 本次启动内的消息序号 |

完整消息编号由以上三部分共同组成，共 10 字节。
source_id 同时也是消息源地址，不应在同一消息头中重复编码。

boot_counter 从 1 开始，每次启动时可靠递增并保存。
sequence 从 1 开始，每创建一条新消息递增。

重传和中继转发不得重新生成消息编号。
计数达到上限时停止创建新消息，不允许直接回绕。
启动计数保存失败时，不允许创建新消息。

擦除持久化存储后，必须重新配置不与历史身份冲突的
source_id，或另行设计身份代次机制。
不得在相同 source_id 下直接从旧编号重新开始。

### 实现注意事项

uint16_t 是 16 位无符号整数，占 2 字节。
uint32_t 是 32 位无符号整数，占 4 字节。

这些是二进制字段长度。
日志中显示的“1-7-12”等文本只是方便阅读的表示方式，
不作为无线报文的实际编码格式。

boot_counter 只在启动时更新，
不应为了每条消息都更新启动计数。
## 第三轮具体设计：本跳 ACK 规则

状态：建议方案，待团队核对和代码验证。

### 1. ACK 的含义

第一版 ACK 表示当前相邻接收节点对消息的处理结果。

ACCEPTED 只表示：
报文校验通过，消息已进入接收节点的内存缓存。

不表示：
- 已写入 Flash。
- 断电后仍可恢复。
- 已到达最终目的节点。
- 最终应用已完成交付。

发送方收到成功 ACK 后，结束本次本跳重试。
消息后续保留或删除，由缓存及交付策略决定，
不能仅因为中继返回 ACK 就直接删除唯一副本。

### 2. ACK 关联信息

ACK 至少包含以下信息：
- 本跳 ACK 发送节点。
- 本跳 ACK 接收节点。
- 被确认消息的完整编号：
  source_id、boot_counter、sequence。
- 处理状态 status。

字段顺序、长度和完整帧编码后续定义。

### 3. 状态值

| 数值 | 名称 | 含义 |
|---|---|---|
| 0 | ACCEPTED | 首次收到，已成功放入内存缓存 |
| 1 | ALREADY_HAVE | 本节点已持有这条消息，或已有其交付记录 |
| 2 | BUSY | 无可用缓存，本次未接收成功 |
| 3 | EXPIRED | 消息已过期，本次拒绝接收 |

status 使用 uint8_t，占 1 字节。
其他数值暂时保留，不得当作成功。

只有仍持有消息或交付记录时，
才可以回复 ALREADY_HAVE。
单独保留一个“曾经见过”的编号，
不能证明消息仍在缓存或已经交付。

### 4. 接收规则

- 长度或 CRC 校验失败：丢弃，不回复 ACK。
- 首次收到并成功缓存：回复 ACCEPTED。
- 已持有消息或已有交付记录：不重复交付，
  回复 ALREADY_HAVE。
- 缓存不足：回复 BUSY，不记录为成功接收。
- 已判定过期：回复 EXPIRED。

消息年龄和过期的具体计算方法后续定义。

### 5. 发送方处理规则

发送方只接受与当前等待消息匹配的 ACK。

必须同时匹配：
- ACK 来自预期的本跳接收节点。
- ACK 发给本节点。
- 完整消息编号相同。
- ACK 帧自身校验通过。

收到 ACCEPTED 或 ALREADY_HAVE：
结束本次本跳重试，不标记最终交付。

收到 BUSY：
结束本轮立即重试，保留有效消息，
等待后续调度机会。

收到 EXPIRED：
结束本轮发送，记录对端拒绝原因；
结合本地有效期规则决定清理，
不能把它记录为送达。

收到不匹配或未知状态的 ACK：
不得据此确认发送成功。

### 6. ACK 丢失示例

1. A 发送消息 X。
2. M 缓存 X，并回复 ACCEPTED。
3. ACK 丢失，A 等待超时。
4. A 使用原消息编号重新发送 X。
5. M 识别出已持有 X，不重复缓存或交付。
6. M 回复 ALREADY_HAVE。
7. A 结束本次本跳重试。

ACK 本身不再请求 ACK，避免无限确认循环。
## 第四轮具体设计：公共帧格式

状态：建议方案，待代码和硬件验证。

### 1. 公共帧布局

| 偏移 | 字段 | 类型/长度 | 说明 |
|---|---|---|---|
| 0 | magic | 2 字节 | 固定为 A5 5A |
| 2 | version | uint8_t | 第一版取 1 |
| 3 | frame_type | uint8_t | 1=DATA，2=ACK |
| 4 | body_length | uint16_t | 正文的字节数，小端序 |
| 6 | body | body_length 字节 | 根据帧类型解析 |
| 6+body_length | crc | uint16_t | CRC 结果，小端序 |

完整帧长度 = 8 + body_length。
正文上限暂定为 160 字节，完整帧最大 168 字节。
该上限是协议设计参数，需经实际模块测试确认。

version=1 是线路上的协议版本号，
不代表当前讨论稿已经冻结。

### 2. CRC 参数

采用 CRC-16/IBM-3740，
也常称 CRC-16/CCITT-FALSE。

参数：
- width：16
- poly：0x1021
- init：0xFFFF
- refin：false
- refout：false
- xorout：0x0000

计算范围：
从 version 开始，到 body 最后一个字节结束。
包括 frame_type 和 body_length。
不包括 magic 和 CRC 字段本身。

CRC 结果以低字节在前的顺序发送。

校验参考：
ASCII 字符串 "123456789" 的 CRC 应为 0x29B1。
对应 CRC 结果的传输字节为 B1 29。
这只是算法校验输入，不是一条完整协议帧。

### 3. 串口解析规则

接收程序按字节流解析。
一次串口读取可能只有半帧，也可能包含多帧。

基本步骤：
1. 搜索 A5 5A。
2. 收齐固定头部。
3. 检查版本、类型和正文长度。
4. 收齐正文和 CRC。
5. 校验通过后，再交给 DATA 或 ACK 处理模块。
6. 处理完一帧后继续解析剩余字节。

不支持的版本、类型或超过上限的长度，
不得进入业务处理。

### 4. 帧头出现在正文中的处理

正文允许包含 A5 5A，不做转义。
已经识别出合法长度、正在收集一帧时，
不得因为正文出现 A5 5A 就立即重新开始。

本方案使用长度和 CRC 共同判断完整性。
帧头本身不能保证一帧有效。

### 5. 错误与恢复

候选帧长度非法或 CRC 失败时，
从该候选帧起点的下一个字节重新搜索帧头，
保留缓冲区中可能属于后续有效帧的字节。

未收齐的帧需要解析超时。
超时后放弃该候选帧并重新搜索。

解析超时值需结合串口输出间隔和模块实测确定，
不能直接套用无线 ACK 超时。

接收缓冲区必须设置容量上限；
缓冲区满时的处理及日志需要明确。
## 第五轮具体设计：DATA 与 ACK 正文布局

状态：建议方案，待团队核对和代码验证。

所有多字节整数使用小端序。
下表偏移从正文第一个字节开始计算，
不包含公共帧头。

### 1. DATA 正文

| 正文偏移 | 字段 | 类型 | 字节数 |
|---|---|---|---|
| 0 | sender_id | uint16_t | 2 |
| 2 | receiver_id | uint16_t | 2 |
| 4 | source_id | uint16_t | 2 |
| 6 | destination_id | uint16_t | 2 |
| 8 | boot_counter | uint32_t | 4 |
| 12 | sequence | uint32_t | 4 |
| 16 | priority | uint8_t | 1 |
| 17 | age_ms | uint32_t | 4 |
| 21 | lifetime_ms | uint32_t | 4 |
| 25 | hop_count | uint8_t | 1 |
| 26 | hop_limit | uint8_t | 1 |
| 27 | payload_type | uint8_t | 1 |
| 28 | payload | 可变长度 | 0～132 |

DATA 正文长度 = 28 + payload 字节数。
DATA 正文长度必须为 28～160。
完整 DATA 帧长度为 36～168 字节。

payload 长度由 body_length - 28 得出，
不另外设置 payload_length。

消息唯一编号为：
source_id + boot_counter + sequence。

### 2. 优先级与载荷类型

priority：
- 0：普通消息。
- 1：重要消息。
- 2：紧急消息。
- 其他值暂不支持。

数值越大，优先级越高。
第一版同级消息按本地入队先后发送。
持续高优先级流量下的防饥饿策略后续定义，
当前不保证普通消息等待时间上限。

payload_type：
- 1：UTF-8 文本。
- 其他值预留。

位置等结构化载荷后续单独定义。
文本不附加 C 字符串的结尾零字节。

132 字节不等于 132 个汉字。
超过载荷上限时明确拒绝，
本阶段不自动截断或分片。

### 3. 年龄与有效期

age_ms 表示消息已经消耗的寿命，
lifetime_ms 表示允许的总寿命，单位均为毫秒。

创建消息时 age_ms = 0。
lifetime_ms 必须大于 0。
当 age_ms >= lifetime_ms 时，消息过期。

节点使用本地单调计时增加消息年龄。
重传、转发不得把年龄重置为 0。
加法使用饱和处理，不允许溢出回绕。

第一版年龄累计方式：
- 创建或接收时，保存年龄基值和本地计时基点。
- 排队期间持续累计本地经过时间。
- 每次发送前更新 age_ms。
- 接收方以收到的 age_ms 建立新的计时基点。

该方式尚未补偿发送取样后到对端接收之间的耗时，
因此年龄可能偏小，不能宣称精确的端到端过期保证。
后续需结合实测明确补偿方式与误差范围。

第一版只支持不断电条件下的年龄累计。
内存缓存消息在重启后丢失；
后续增加持久化时，必须处理停机期间的年龄，
不得将恢复消息当作新消息。

### 4. 跳数规则

hop_limit 表示允许经过的最多无线链路数。
创建时 hop_count = 0，hop_limit 必须大于 0。

准备发送时：
- 若本地 hop_count >= hop_limit，不再发送。
- 否则，在线路报文中填写本地 hop_count + 1。

重试同一跳时，发送相同的跳数值，
不能每重试一次就增加一次。

接收方要求：
1 <= hop_count <= hop_limit。

到达最终目的节点时，即使 hop_count = hop_limit，
仍可以接收并尝试交付。
中继节点达到 hop_limit 后不得继续转发。

### 5. ACK 正文

| 正文偏移 | 字段 | 类型 | 字节数 |
|---|---|---|---|
| 0 | sender_id | uint16_t | 2 |
| 2 | receiver_id | uint16_t | 2 |
| 4 | source_id | uint16_t | 2 |
| 6 | boot_counter | uint32_t | 4 |
| 10 | sequence | uint32_t | 4 |
| 14 | status | uint8_t | 1 |

ACK 正文长度必须为 15 字节。
完整 ACK 帧长度为 23 字节。

sender_id 是回复 ACK 的节点。
receiver_id 是收到 ACK 的节点。
其余编号字段引用被确认的 DATA 消息。

status：
- 0：ACCEPTED
- 1：ALREADY_HAVE
- 2：BUSY
- 3：EXPIRED

ACK 不再次请求 ACK。

### 6. 接收检查

只有公共帧校验及正文检查均通过，
才允许修改消息缓存或交付业务。
