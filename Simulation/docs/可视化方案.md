# 可视化方案（第二阶段 · 灾害场景）

> 目标：把「孤岛之间靠移动节点存储-携带-转发」这件事**看得见**。
> 当前进度：模拟数据 + 电脑端地图回放已经能跑，截图在 `docs/shots/`。

## 一、先回答那个问题：手机还是电脑？

结论：**先做电脑端，手机端留一个几乎零成本的移植口**。理由是三条路都试过成本：

| 路线 | 需要什么 | 真实代价 | 现在能不能做 |
|---|---|---|---|
| Android 原生 / Flutter App | JDK + SDK + Gradle/Flutter，签名、装机、改一次装一次 | 2–3 天打底，且和「画地图」无关 | 要装一大堆东西 |
| 手机浏览器 + Web Bluetooth | 只支持 Android Chrome；iOS Safari **不支持** Web Bluetooth | 半天，但 iPhone 直接白屏，答辩时很尴尬 | 能做，覆盖面窄 |
| **电脑端（当前做法）** | Python + tkinter，零第三方依赖 | 已经跑起来了 | ✅ 已完成 |
| 手机浏览器 + ESP32 自建热点 | ESP32 开 SoftAP + 网页服务，手机连它的 WiFi 打开网页 | 1–2 天，**任何手机都行**，不用装 App | 建议作为「要手机」时的方案 |

关键点：**数据通路完全一样**。手机上不管哪种方案，吃的都是同一份 JSONL 日志；
所以「解析 → 状态 → 绘制」这三层现在写对了，将来换前端只换最外面那层皮。

> 如果你就是想「演示时拿手机给人看」，最划算的是第四条：ESP32 起个热点，
> 手机浏览器打开 `192.168.4.1`，页面用同一套字段画图。不需要写 App，也不需要 BLE。

## 二、已跑通的东西

```
第二阶段/
  visual/simulate.py     灾害场景仿真：孤岛 + 固定节点 + 会走路的移动节点
  visual/mapview.py      地图回放窗口（tkinter，离线，无第三方依赖）
  visual/tools/shoot_map.py  自动截图
  sim/trace.jsonl        位置快照（每 5 秒一帧，给地图用）
  sim/log.jsonl          V1 日志（253 条，喂给 logview 校验）
  docs/shots/map-*.png   四张截图：开局 / 携带中 / 首次送达 / 末段
```

场景设定（`visual/simulate.py`）：

- 三个孤岛 A（北岸营地）、B（河谷中转站）、C（南坡搜救点），间距 400 m；
- 每岛两个固定节点，LoRa 半径 160 m —— **小于岛间距，所以直连不可能**，
  必须靠移动节点把消息带过去；
- 两个移动节点（驴友-甲、驴友-乙）在 A↔B、B↔C 之间往返，路上边走边收发；
- 转发策略先用最朴素的 **epidemic（人人存副本、见面就交换）**：好理解、好演示，
  缺点是副本多、耗电，后面再上 TTL/限额。

跑出来的结果（`python visual\simulate.py --out sim`）：

```
消息 7 条，15 分钟内送达 6 条，跨岛平均耗时 3–6 分钟，最长一条到 880 s 才送到
交付明细：
  消息#3 2→4  150s 创建，480s 送达（经移动节点 7）
  消息#1 1→6   30s 创建，495s 送达（经 7、8）
  消息#2 6→1   75s 创建，655s 送达（经 7、8）
```

**并且这份模拟日志通过了队友的 V1 规范校验**：

```
python -m logview check sim\log.jsonl
→ log.jsonl: 253 条有效记录，0 条导入错误
python -m logview summary sim\log.jsonl
→ 消息 1-7-1 目的 6，本跳确认 2,3,4,6,7,8，状态「已最终交付」
  消息 5-7-5 目的 2，本跳确认 3,4,6,7,8，状态「本跳已确认（未到终点）」
```

也就是说：**模拟器产出的日志和板子将来要吐的日志，走的是同一套解析器和同一套状态判定**。
将来你给的 ESP32 真实日志一接进来，界面不用改。

## 三、灾难场景这套系统大概怎么搭

分层看，四层，各自可以独立替换：

```
① 射频/节点层   ESP32-S3 + LoRa 模块，孤岛内组网（现在 Ra-02/LLCC68 已验证可通）
② 携带层        移动节点（驴友设备）边走边收，存到 flash，遇到下一个孤岛再发
③ 语义层        消息编号、ACK、去重、有效期（protocol-v1 / log-v1 已经定义）
④ 展示层        电脑端地图回放 → 以后可以是手机网页 / 指挥中心大屏
```

演示剧本（也是答辩时最好讲的故事）：

1. 南坡搜救点发一条求救（孤岛 C 内部先传开）；
2. 驴友-乙从 C 走到 B，路上把消息收进口袋（**存储**）；
3. 到 B 交给营地中继（**携带 + 转发**）；
4. 驴友-甲从 B 往 A 走，再送一程，最终营地收到（**多跳交付**）；
5. 界面上能看见：消息在哪一秒被谁收下、走了哪几跳、哪条路断过。

## 六、已知限制（别在答辩时被问住）

- 位置是**模拟的**，不是实测 GPS；界面上有 `SIM` 标记，别当成真实轨迹；
- 单条消息最长延迟接近 15 分钟才送达 —— 这是 store-carry-forward 的**真实代价**，
  不是 bug，讲的时候要主动说明「为什么慢」；
- 转发是 epidemic，副本数量会随节点数指数增长，规模上去必须限额；
- 空口速率 2149 bps（LEVEL=2），一条 39 字节帧大约 0.15 s，链路上说话的机会很有限。
